# MVP 技术实现文档

## 1. 文档状态

- 状态：技术核查完成，Web 首版骨架已实现
- 对应产品文档：[MVP产品需求文档.md](./MVP产品需求文档.md)
- 对应交互文档：[Design.md](../Design.md)
- 首版部署形态：桌面 Web 应用；微信小程序作为浏览和订阅入口
- 首版使用范围：你本人及内部账号

## 2. 技术核查结论

### 2.1 可直接落地的能力

- Web 首页、趋势列表、内容详情、审核中心和设置页面。
- 个人关注词与后端行业关键词管理。
- 采集任务调度、增量窗口、重试和任务日志。
- 内容标准化、去重、趋势聚合、互动数据存储和一周自动清理。
- 整份摘要编辑、权限分离、最终审核、审核日志和版本校验。
- 企业微信应用消息推送到指定成员，前提是完成企业应用和可见范围配置。
- 飞书机器人群推送。
- 飞书多维表格每天写入一条最终摘要记录，并对失败任务重试和告警。

### 2.2 不能仅依靠官方开放 API 完成的能力

- 三个平台统一的通用行业关键词检索。
- 小红书、抖音、视频号完整覆盖 1 天、3 天、7 天、30 天窗口。
- 三个平台都稳定提供封面、作者、点赞、收藏、评论和原文链接。
- 对所有行业词识别头部账号并计算跨平台趋势。

首版必须将外部爬虫软件或已授权数据服务作为主要采集来源。系统不直接把爬虫实现写死在业务层，而是定义统一的采集适配接口，使三个来源可以独立替换、重试和降级。

### 2.3 关键限制

抖音官方“视频搜索管理”文档说明：开发者申请与自身业务相关的关键词后，可搜索标题含关键词的公开视频、查看评论；搜索结果只返回最近 1 天发布的视频，且关键词不得为通用品类词或竞品品牌词。因此它不能单独支撑本产品的通用行业监测和 1/3/7/30 天历史窗口。

微信小程序订阅消息需要用户主动订阅。一次性订阅消息的用户授权与可发送次数受模板和用户授权状态约束；不能把小程序理解为无需用户动作、每天固定三次无限推送的通道。07:00、12:00、18:00 的稳定通知应以企业微信或飞书为主，小程序作为用户主动订阅后的服务通知和站内入口。

飞书自定义机器人 Webhook 只能向添加它的群组单向推送；如果要给指定用户单聊、发送交互卡片或获取更完整的用户与会话能力，应使用飞书应用机器人并完成权限、可用范围和应用发布配置。

## 3. 推荐系统边界

```text
外部爬虫 / 授权数据源
        ↓
采集适配层（小红书 / 抖音 / 视频号）
        ↓
标准化与去重
        ↓
内容库（原始内容保留 7 天）
        ↓
趋势聚合与摘要草稿
        ↓
审核工作流（编辑者 → 固定发布者 / 备用发布者）
        ├── Web 首页 / 审核中心
        ├── 企业微信推送
        ├── 飞书机器人推送
        ├── 微信小程序服务通知 / 页面入口
        └── 每日晚间飞书多维表格归档
```

## 4. 推荐技术模块

### 4.1 Web 应用

职责：

- 登录和内部账号权限；
- 今日总览首页；
- 平台分类按钮和趋势发现；
- 内容详情和原文跳转；
- 审核中心；
- 关注词和行业关键词设置；
- 任务状态、失败原因和手动重试。

实现要求：

- 以当前 `Design.md` 为 UI/UX 约束；
- 首屏保留“今日趋势 / 审核状态 / 重点内容”的三块结构；
- 平台分类只更新趋势列表，不刷新整个页面；
- 审核提交必须做摘要版本校验和幂等控制；
- 原文跳转不能丢失当前情报页面状态。

### 4.2 API 服务

职责：

- 为 Web 和小程序提供统一数据接口；
- 校验用户权限和摘要版本；
- 管理关注词、行业关键词和推送配置；
- 创建采集、聚合、审核、推送和归档任务；
- 返回局部更新状态，避免首页被全量刷新。

### 4.3 任务调度与工作流

至少需要以下任务类型：

| 任务 | 触发方式 | 作用 |
|---|---|---|
| platform_collect | 定时 / 手动 | 调用平台采集适配器获取新增内容 |
| normalize_content | 采集后 | 统一字段、时间和来源格式 |
| deduplicate_content | 标准化后 | 跨平台去重和同源去重 |
| aggregate_trends | 采集后 | 按主题聚合、计算出现次数和平台覆盖 |
| generate_digest | 聚合后 / 手动 | 生成整份待审核摘要 |
| notify_reviewers | 摘要生成后 | 通知编辑者和发布者 |
| publish_digest | 审核通过后 / 重试 | 推送至已配置渠道 |
| archive_daily_digest | 每晚 | 写入飞书多维表格一条最终摘要记录 |
| cleanup_content | 每日 | 删除网站中超过 7 天的原始内容和中间数据 |

任务必须有唯一业务键，例如：

```text
collect:{platform}:{window_start}:{window_end}
digest:{business_date}:{delivery_slot}:{revision}
publish:{digest_id}:{channel}:{revision}
archive:{business_date}
```

同一业务键重复执行不得产生重复摘要、重复推送或重复归档记录。

## 5. 采集适配层

### 5.1 统一输入

```json
{
  "platform": "xiaohongshu | douyin | channels",
  "keywords": ["关注词"],
  "startTime": "ISO-8601",
  "endTime": "ISO-8601",
  "cursor": "optional",
  "sourceJobId": "string"
}
```

### 5.2 统一输出

```json
{
  "platform": "xiaohongshu | douyin | channels",
  "externalId": "string",
  "title": "string",
  "coverUrl": "string | null",
  "publishedAt": "ISO-8601",
  "author": {
    "id": "string | null",
    "name": "string",
    "followers": "number | null",
    "isTrackedCreator": "boolean | null"
  },
  "summary": "string | null",
  "likeCount": "number | null",
  "favoriteCount": "number | null",
  "commentCount": "number | null",
  "comments": [],
  "sourceUrl": "string | null",
  "matchedKeywords": ["string"],
  "collectedAt": "ISO-8601",
  "rawPayloadRef": "string | null"
}
```

### 5.3 采集降级规则

- 某平台失败不阻塞其他平台入库、聚合和审核草稿生成。
- 每个平台单独记录 `healthy / delayed / failed / recovering` 状态。
- 失败平台按退避策略自动重试；恢复后只补采缺失时间窗口，避免重复入库。
- 缺失字段使用 `null`，不使用虚假 0 填充。
- 采集来源必须保留原始记录引用和采集时间，以便排查数据问题。
- 爬虫软件的登录态、Cookie、代理和账号配置不进入 Web 前端，也不写入普通业务日志。

## 6. 内容标准化、去重与趋势聚合

### 6.1 去重层级

1. 同平台同 `externalId` 去重；
2. 同平台同源链接去重；
3. 跨平台使用标题、摘要、关键词和发布时间窗口做近似匹配；
4. 近似匹配只用于候选聚合，不能直接删除原始内容。

### 6.2 趋势条目最小字段

- 趋势 ID；
- 趋势标题；
- 一句话解读；
- 关联内容数；
- 覆盖平台；
- 关联关键词；
- 关联作者数；
- 头部作者信号；
- 时间窗口；
- 热度变化值；
- 置信或质量标记；
- 生成版本和审核状态。

### 6.3 首版排序建议

在没有历史标注数据前，趋势排序先使用可解释规则，不直接声称“预测趋势”：

```text
趋势分 =
  近窗口内容频率权重
  + 跨平台覆盖权重
  + 互动量变化权重
  + 头部账号参与权重
  + 时间新鲜度权重
```

具体权重和阈值属于待验证配置，必须可在后台调整，不应写死在前端。

## 7. 摘要与审核工作流

### 7.1 状态机

```text
COLLECTING
  → DRAFT_GENERATED
  → EDITING
  → PENDING_FINAL_REVIEW
  → APPROVED
  → PUBLISHING
  → PUBLISHED

任意发布前状态 → FAILED（可修复后回到原状态）
PENDING_FINAL_REVIEW → REJECTED / EDITING
```

### 7.2 权限

| 角色 | 可做操作 |
|---|---|
| 编辑者 | 查看草稿、修改摘要、删除不相关内容、调整趋势顺序 |
| 固定发布者 | 查看最终版本、审核通过、触发发布 |
| 备用发布者 | 在固定发布者不可用时执行最终审核和发布 |
| 只读内部账号 | 查看首页、趋势和内容；不能修改或发布 |

### 7.3 版本与并发

- 每次编辑生成递增版本号。
- 发布请求携带 `digestId + revision`。
- 服务端只接受当前 revision，旧版本请求返回“内容已更新”。
- 发布接口必须幂等；同一摘要、同一渠道、同一版本最多产生一条成功投递记录。
- 审核日志保存编辑人、审核人、发布时间、版本号和修改摘要。

### 7.4 审核通过与推送关系

产品意图要求“审核通过后推送”，因此 MVP 默认将审核通过视为触发当前批次推送，而不是只改变状态。若后续决定必须等待固定时刻，则需将状态拆成 `APPROVED_WAITING_DELIVERY`，这属于产品规则变更。

## 8. 定时推送

### 8.1 三个时段

- 07:00；
- 12:00；
- 18:00；
- 默认时区：Asia/Shanghai。

### 8.2 增量规则

- 每次摘要以该时段上一次成功处理的游标为起点。
- 只纳入游标之后的新内容。
- 无新增但存在上一份已审核摘要时，复用上一份已审核摘要并标记为“重复提醒”。
- 首次运行且没有历史审核摘要时跳过推送。
- 摘要审核超过计划时间时延迟发送，不发送未经审核版本。

### 8.3 渠道适配

#### 企业微信

推荐作为定时通知主渠道之一：

- 通过企业应用消息向指定成员发送文本卡片或图文消息；
- 消息中包含摘要、重点内容和 Web 入口；
- 配置应用可见范围、接收人 ID、AgentId 和 access token 获取方式；
- 记录每个接收人的成功、无权限和无效用户结果；
- 开启重复消息检查或由系统业务键保证幂等。

#### 飞书

两种接入模式：

1. 自定义机器人 Webhook：适合向指定群单向推送，配置成本低；
2. 应用机器人：适合指定用户单聊、交互卡片和更完整的权限管理。

MVP 可先使用自定义机器人 Webhook 完成群推送；若“指定用户”是硬要求，应直接采用应用机器人。

#### 微信小程序

- 小程序用于浏览每日情报和打开详情页。
- 消息通知必须让用户在小程序内主动订阅对应模板。
- 首版不把小程序作为三次定时推送的唯一可靠通道。
- 发送前检查用户是否仍有对应模板的订阅权限；无权限时记录跳过原因，不影响企业微信和飞书推送。
- 订阅消息点击后只能跳转到已配置的小程序页面路径；不能把任意外部站点当作小程序内部页面直接依赖。

### 8.4 推送失败处理

- 每个渠道独立重试，不因一个渠道失败而回滚其他渠道成功结果。
- 采用指数退避，重试次数与间隔作为配置项。
- 超过重试上限后生成失败告警，并在审核中心保留“部分渠道失败”状态。
- 手动重试必须复用原摘要版本和业务键，不能重新生成摘要。

## 9. 飞书多维表格归档

### 9.1 归档时机

每天晚上执行一次，写入当天最后一次已审核并推送的最终摘要。

### 9.2 一条记录字段

- 日期；
- 摘要正文；
- 涉及平台；
- 关键词；
- 重点内容；
- 原文链接；
- 可选系统字段：摘要 ID、版本号、归档时间、推送结果。

### 9.3 幂等与失败

- 以业务日期作为唯一归档键。
- 当天重复执行应更新同一天记录，而不是新增重复记录。
- 写入失败自动重试并告警。
- 飞书应用需要成为目标多维表格所有者或协作者，并具备相应记录写入权限。
- 飞书多维表格长期保存，网站原始数据清理不影响已归档摘要。

## 11. 存储与保留策略

- 原始内容、封面缓存引用、评论片段和中间聚合数据默认保留 7 天。
- 摘要、审核日志、推送记录至少保留到产品可复盘周期结束；若需要长期留存，归档到飞书多维表格或另设历史库。
- 不在数据库中保存爬虫账号明文密码、Cookie 或 Webhook 密钥；使用密钥管理服务或部署环境密钥。
- 原文 URL、作者信息和评论数据按最小必要原则保存。
- 清理任务必须可审计，避免误删飞书归档数据。

## 12. 可靠性与观测

必须记录以下指标和日志：

- 每个平台采集成功率、延迟、返回条数和失败原因；
- 标准化、去重和趋势聚合耗时；
- 摘要生成到人工审核的等待时间；
- 审核通过到各渠道送达的耗时；
- 各渠道成功、失败、重试和部分成功次数；
- 飞书归档成功率和重复写入拦截次数；
- 网站 API 错误率和页面数据新鲜度。

30 分钟要求应定义为：从某个推送窗口的采集任务开始，到“可进入人工审核”的摘要草稿生成完成不超过 30 分钟。人工审核耗时不应伪装为系统处理延迟；如果业务要求从采集到最终推送不超过 30 分钟，则当前“人工审核”要求会形成冲突，需要另行确认。

## 13. 技术风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 平台采集被限流或登录失效 | 缺数据、延迟推送 | 适配器隔离、健康状态、重试、部分平台降级 |
| 平台字段不完整 | UI 缺封面或互动数 | 字段允许为空，前端固定占位并显示数据时间 |
| 跨平台误聚合 | 趋势判断失真 | 仅做候选聚合，保留原始内容和人工反馈 |
| 审核并发冲突 | 旧摘要被发布 | revision 乐观锁和发布幂等键 |
| 小程序订阅不足 | 无法保证三次通知 | 企业微信/飞书作为主通知，小程序作为补充 |
| 推送部分成功 | 用户收到不一致消息 | 渠道独立状态、部分成功提示、独立重试 |
| 飞书 Webhook 泄露 | 被滥发消息 | 密钥托管、后台脱敏、定期轮换和安全设置 |
| 30 分钟与人工审核冲突 | SLA 无法兑现 | 拆分系统处理 SLA 和人工审核 SLA |

## 14. 实施顺序

### Phase 1：数据与流程骨架

- 建立用户、关键词、内容、趋势、摘要、审核日志和投递记录模型；
- 接入一个可用的爬虫数据源适配器；
- 完成一周保留和任务日志；
- 完成摘要草稿和人工审核状态机。

### Phase 2：Web 首屏与审核中心

- 按 `Design.md` 实现每日总览首页；
- 完成平台分类、趋势行、重点内容、审核预览和审核中心入口；
- 完成编辑者 / 发布者权限与版本校验；
- 完成手动采集、重新生成和重试入口。

### Phase 3：推送与归档

- 接入企业微信指定用户消息；
- 接入飞书机器人；
- 接入飞书多维表格每日归档；
- 增加渠道独立重试、失败提醒和幂等校验。

### Phase 4：小程序与第二、第三平台

- 实现小程序登录、每日情报浏览和详情页；
- 配置并验证订阅消息模板和用户授权流程；
- 接入剩余平台采集适配器；
- 用真实数据校验跨平台聚合准确率和数据完整性。

## 15. 当前阻断项与前置配置

开始正式编码前需要准备：

1. 爬虫软件的输出协议、回调地址或数据库访问方式；
2. 三个平台各自可采集的字段清单和合规授权说明；
3. 企业微信 CorpID、AgentId、应用可见范围和接收人 ID；
4. 飞书机器人类型、Webhook 或应用凭证、目标群 / 用户；
5. 飞书多维表格的 `app_token`、`table_id` 和目标字段名；
6. 微信小程序 AppID、订阅消息模板 ID、业务域名和页面路径；
7. 固定发布者、备用发布者和编辑者账号清单；
8. 趋势排序初始权重和“头部账号”的配置规则；
9. 30 分钟 SLA 是指“摘要草稿可审核”还是“最终推送完成”。

## 16. 结论

本 MVP 技术上可以实现，但必须采用“外部爬虫 / 授权数据源 + 统一采集适配层”的方案。当前 Web 首版已包含 MediaCrawler 文件读取、独立可写输出目录、后端关键词配置、定时调度和 Agent 分析骨架。每轮任务按“采集 → 同步 → Agent 分析 → 生成趋势与审核草稿”执行；Agent Prompt 保存在 `config/automation.json`，未配置远程模型时回退本地规则。Web、审核、企业微信、飞书推送和飞书多维表格归档可以进入开发；微信小程序通知需要按用户订阅能力设计，不能承诺无条件三次主动推送；三平台通用历史检索和完整字段覆盖不能由当前可确认的官方开放 API 单独保证。
